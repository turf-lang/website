## What a style guide is

Think of a classroom where everyone keeps notes in the same way: the date in the top corner, headings underlined, one idea per line. None of that changes what the notes *say*. It means you can pick up a friend's notebook and find your way around it at once.

A **style guide** does the same for code. The compiler does not care whether you indent with two spaces or eight, or whether a function is called `TotalPrice` or `total_price`. People do. Code is read many more times than it is written, and most of those reads are by someone who did not write it, including you, six months later.

Here is one program written twice. Both compile and both print `12`.

<DoDont file="tsg_intro">
```turf
fn area(width: int, height: int): int {
    return width * height;
}

fn main(): int {
    immut w: int = 3;
    immut h: int = 4;
    printline(area(w, h));
    return 0;
}
```
```turf
fn AREA(W:int,H:int):int{
return W*H;}
fn main():int{immut a:int=3;immut B:int=4;
printline(AREA(a,B));return 0;}
```
</DoDont>

The second one works. It is just tiring to read, and every reader pays that cost again.

## How to read a rule

Every rule in the guide has the same four parts:

1. **A number**, such as `TSG-101`. The number never changes and is never reused for another rule, so you can quote it in a code review, a commit message or a diagnostic and it always means the same thing.
2. **A level.**
   - **Required** means everyone follows it, and a tool will eventually check it for you.
   - **Recommended** means it is good advice, and you can break it when you have a reason.
3. **Which tool checks it**, if any. Today only `turf fmt` checks anything, and only four rules.
4. **Two examples**: one to copy (**Do**) and one to avoid (**Don't**). Both are real programs, and both compile.

The first digit of the number tells you which page the rule is on:

| Numbers | Page | What it covers |
|---|---|---|
| `TSG-1xx` | [Indentation](/tsg/indentation/) | spaces, blank lines, line length |
| `TSG-2xx` | [Identifier naming](/tsg/naming/) | what to call things |
| `TSG-3xx` | [Import organization](/tsg/imports/) | file names, imports and the order of a file |
| `TSG-4xx` | [Function and type formatting](/tsg/functions-and-types/) | braces, spacing, lists and `compare` |
| `TSG-5xx` | [Error-handling conventions](/tsg/errors/) | `!T`, panics and error messages |
| `TSG-6xx` | [Public API documentation](/tsg/public-api/) | comments and `pub` |
| `TSG-7xx` | [Idiomatic Turf](/tsg/idioms/) | which form to pick when there are several |
| `TSG-8xx` | [Safety](/tsg/safety/) | `unsafe`, C code and resources |

## Where the guide is going

The guide is **new**. It is written now, it grows and settles during Turf 2.x, and at Turf 3.0 the formatter learns it.

<Flow caption="From a draft today to a formatter that applies it.">
<FlowStep label="Now">the rules are written down and discussed</FlowStep>
<FlowStep label="Turf 2.x">rules are added, argued over and settled</FlowStep>
<FlowStep label="Before 3.0">the formatting rules are frozen</FlowStep>
<FlowStep label="Turf 3.0">`turf fmt` applies every required formatting rule</FlowStep>
</Flow>

- **Until 3.0, `turf fmt` does not change.** It keeps doing exactly the four things it does today ([TSG-101](/tsg/indentation/#tsg-101-indent-with-four-spaces) to [TSG-104](/tsg/indentation/#tsg-104-end-every-file-with-one-newline)), so the formatter's output stays the same across every 2.x release while the guide is still moving.
- **Before 3.0, any rule can still change.** No tool enforces the new rules yet, so changing one breaks nobody's build.
- **At 3.0**, the formatting rules are frozen and `turf fmt` is updated to apply them, all at once. A project adopts them by running `turf fmt --write` one time.
- **After 3.0**, a new formatting rule lands in this guide and in `turf fmt` together, and a rule that changes what `turf fmt` outputs is listed in the release notes.

<Callout tone="note" title="This guide is a draft">

The rules in this guide describe Turf as it is today, in 2.x. The plan is tracked in [turf-lang#281](https://github.com/turf-lang/turf-lang/issues/281); comment there if you disagree with a rule or want a new one.

</Callout>

## Changing the guide

The guide belongs to everyone who writes Turf. To suggest a new rule or argue against one, open an issue on [turf-lang/turf-lang](https://github.com/turf-lang/turf-lang/issues) or comment on [turf-lang#281](https://github.com/turf-lang/turf-lang/issues/281). A good suggestion says which rule, what should change, and shows a short piece of real code where the change helps.

Rules are changed carefully, not on a timetable:

- A settled rule stays settled unless there is a strong reason to change it.
- New syntax gets its rules in the same release that ships it, never before.
- A rule that is removed keeps its number, marked as withdrawn, so old references still lead somewhere.
